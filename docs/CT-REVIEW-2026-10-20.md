# CT 개발 중간 재검토와 다음 실행 순서

검토일: 2026-10-20. 코드 기준: M3o / `d86d916`.
성격: 현재 코드·기존 실행 증거·공식 외부 자료를 대조한 전략 검토와 제안.
기능 구현, main 병합, 외부 엔진 채택을 이번 문서로 실행한 것은 아니다.
기존 [전체 목표](CT-COMPLETION-GOALS.md)와 [P00~P25 로드맵](CT-EXECUTION-ROADMAP.md)을
대체하는 전체 설계가 아니라, 그 안의 다음 작업 순서를 재조정하는 제안이다.

## 1. 판단

CT의 방향은 유지할 가치가 있다. 현재 구현은 단순 문법 변환 데모를 넘어
**CUDA Driver ABI → PTX/fatbin → 타입 있는 IR → SPIR-V → Arc GPU**를 연결한다.
사용자 공간의 Rust 호환 계층으로 개발하며 제조사의 장치 드라이버를 하부에 사용한다.
시스템 디스플레이 드라이버를 새로 만드는 작업은 아니다.

현재 수준은 **한 Intel GPU에서 검증한 제한된 CUDA Driver 호환 프로토타입**이다.
일반 설치형 CUDA 앱, PyTorch CUDA 패키지 또는 범용 CUDA 대체 제품으로 보기는 이르다.
완료율은 정하지 않는다. 명령·API·라이브러리·앱은 작업량과 영향이 서로 다르다.

가장 큰 수정 권고는 **앱과 연결되지 않은 P03 소규모 연산 확장을 주 실행선에서 멈추고,
고정한 기존 앱의 최초 실패를 기준으로 기능을 선택하는 것**이다. P03은 계속 필요하지만
그 자체의 완성을 일반 앱 연결의 불필요한 선행 조건으로 두지 않는다.

## 3. 현재 막히는 지점

### 3.1. 일반 앱이 요구하는 시작·등록 계약

현재 cuDriverGetVersion은 의도적으로801/0을 반환하고 장치 속성도 제한된 항목만 제공한다.
cuLaunchKernel은 nonnull stream, dynamic shared memory 및 packed extra 인자를 거부한다.
이런 조건은 PTX의 산술 연산까지 도달하기 전에 일반 앱을 중단시킬 수 있다.
거짓 버전·기능을 광고해서 통과시키는 해결책은 사용하지 않는다.

cuModuleLoadData로 외부 fatbin을 읽는 것과 일반 nvcc 프로그램이 cudart를 통해 내장
fatbin·커널을 등록하는 것은 별도 경로다. Driver 함수26개를 갖췄다고 Runtime이 자동으로
연결되는 것은 아니다. primary context, 등록/해제, 오류 상태, Driver/Runtime 공동 상태가 필요하다.

근거: [CUDA 계층](../crates/ct-cuda/src/lib.rs),
[launch](../crates/ct-cuda/src/modules.rs), [fatbin 프로파일](compatibility/fatbin-profile.md).

### 3.2. 앱 목록과 증거 단계

로드맵은 docs/compatibility/applications.json에 앱·버전·의존성·해시·정답을 고정하도록
요구하지만, 검토 시 이 파일은 없다. 최근 M3m~M3o는 주로 합성 Python CUDA 소비자와
기존 C 소비자의 회귀 검증이다. 앞으로의 기능 선정 근거가 되는 실제 앱 집합이 필요하다.

외부 실행 증거는 다음 네 단계로 구분한다.

1. CT가 만든 합성 host/kernel: API·명령의 통제된 검증.
2. 수정하지 않은 외부 소스를 조정된 빌드/모듈 생성 경로로 재빌드: 현재 vectorAddDrv 증거.
3. 수정하지 않은 외부 소스를 원래 빌드 절차로 빌드하고 그 artifact를 고정해 실행.
4. 이미 배포된 기존 실행 파일과 GPU 코드·의존 파일을 고정해 변경 없이 실행.

각 단계는 유용하지만 서로 대체하지 않는다. 확보하지 못한 artifact는 pending으로 기록하고
소스 재빌드 결과를 배포 바이너리 호환으로 표시하지 않는다. 앱 실행 중 executable/GPU 코드의
해시 보존은 모든 단계의 공통 조건이며, 그 자체로4단계 증거가 되지는 않는다.

### 3.3. 검증·통합 관리

- 공식 spirv-val이 아직 검증 경로에 없다. Arc 드라이버가 받아들인 사실만으로 다른
  compiler/driver에도 유효한 SPIR-V라고 결론 내릴 수 없다.
- manifest의 일부 export 시험 참조는 실제 API 호출 동작보다 resolver 경계를 가리킨다.
  resolver/서명 검사와 할당·복사·수명 등 behavior 호출 시험을 나누어 연결해야 한다.
  manifest 파일 유효성은 시험 실행 성공이 아니다.
- 검토 시 GitHub PR1~18은 모두 OPEN/DRAFT이며 적층되어 있다. main은
  `64ff908` 설계 기록에 머물러 있다. 개발 브랜치의 구현과 main/릴리스 상태를 구분해야 한다.
- 일반 CI workflow 파일은 현재 확인되지 않았다. CPU·parser·codegen·ABI·공개 검사와
  준비된 vendor/native fixture·Arc 실행을 분리한 자동 검증 목록이 필요하다.
- 이후 동시성에는 전역 mutex와 동기 실행 경로의 재검토가 필요하다. 현재 경로를
  그대로 비동기라고 부르거나 완료 전 자원을 해제해서는 안 된다.

## 4. 기존 접근과 참고할 것

외부 자료는 2026-10-20 공식 저장소/문서에서 확인했다. 아래 지원 설명은 해당 프로젝트의
공개 설명이며 CT 노트북에서 설치·실행·성능 비교한 결과가 아니다.

| 기술 | 입력·실행 방식 | CT와의 관계 및 활용 |
| --- | --- | --- |
| [ZLUDA](https://github.com/vosen/ZLUDA) | 기존 CUDA 앱 실행 호환 계층 | 목표가 가장 가깝다. API/컴파일러/라이브러리/앱 회귀 구조를 비교할 가치가 크다. [공식 FAQ](https://zluda.readthedocs.io/latest/faq.html)는 현재 Intel 지원이 없고 AMD에 집중한다고 설명한다. Arc용 즉시 대체재로 가정하지 않는다. |
| [SCALE](https://docs.scale-lang.com/stable/) | CUDA 소스를 자체 nvcc 대체 컴파일러로 재컴파일하고 CUDA API/라이브러리 계층 제공 | 대상 앱별 API coverage와 library adapter 설계를 참고한다. 현재 문서는 AMD/NVIDIA를 대상으로 하며 [FAQ](https://docs.scale-lang.com/stable/manual/faq/)는 Windows 미지원으로 설명한다. 기존 NVIDIA 실행 파일을 CT에서 그대로 실행하는 경로와 구분한다. |
| [chipStar](https://github.com/CHIP-SPV/chipStar) | HIP/CUDA 소스를 SPIR-V로 컴파일하고 OpenCL/Level Zero로 실행 | Intel 실행 경로·인자·메모리·동기화 설계의 유용한 비교 대상. 소스 재컴파일 경로이며 CT의 PTX/기존 host ABI를 자동 대체하지 않는다. Windows/B390 실현성은 CT에서 미검증이다. |
| [AdaptiveCpp PCUDA](https://github.com/AdaptiveCpp/AdaptiveCpp/blob/develop/doc/pcuda.md) | CUDA/HIP 계열 소스를 portable CUDA dialect로 컴파일, generic JIT backend 사용 | 실험적 다중 backend 모델. 프로젝트가 assembly/binary 재컴파일 도구가 아니라고 명시한다. backend 분리와 실행 의미를 참고하되 기존 CUDA 바이너리 호환과 혼동하지 않는다. |
| [HIPIFY](https://github.com/ROCm/HIPIFY) / [SYCLomatic](https://github.com/oneapi-src/SYCLomatic) | CUDA 소스를 HIP/SYCL로 옮겨 재빌드 | 이식 도구와 API 대응표·시험 corpus를 참고할 수 있다. CT의 자체 기존 앱 실행 목표는 유지한다. |
| [SPIRV-Tools](https://github.com/KhronosGroup/SPIRV-Tools) | 생성된 SPIR-V 검증·분석·변환 도구 | 우선 도입할 개발 기반. 출력 프로파일에 맞는 환경으로 검증하고 도구 버전·진단을 기록한다. validator 통과도 PTX 의미 동등성이나 실제 GPU 성공의 대체는 아니다. |

ZLUDA의 확인한 [2026-06-29 공식 보고](https://vosen.github.io/ZLUDA/blog/zluda-update-q1q2-2026/)는
v6와 Windows·실제 workload 개선을 설명한다. 오래된 FAQ의 자금·예정 일정은 이 보고와
다를 수 있으므로 현재 사실로 옮기지 않았다. 공식 발표의 성능 수치도 CT 성능으로 사용하지 않는다.

별도 참고: [PyTorch의 Intel XPU 경로](https://docs.pytorch.org/docs/main/notes/get_start_xpu.html)는
Intel에서 AI를 직접 실행하는 경로와 비교 기준으로 조사할 수 있다. CUDA 패키지 호환 성공으로
세지 않으며, 이 노트북의 구체적 모델·OS·버전 조합 지원을 이 문서가 보장하지 않는다.

## 5. 개발 방식 선택

| 선택 | 장점 | 비용/판단 |
| --- | --- | --- |
| 기존 방식대로 P03 세부 명령을 계속 우선 | 작고 검증하기 쉬운 진전 | 새 일반 앱이 열리지 않아도 진행으로 보일 위험. 주 실행선으로 권하지 않는다. |
| CT 소유 ABI·컴파일러를 유지하고 앱 실패를 중심으로 확장 | 사용자 목표와 현재 자산을 살리고 효과를 측정 가능 | 권고안. 표준 검증 도구·공식 명세·타 프로젝트 설계를 적극 참고한다. |
| ZLUDA 등으로 핵심을 교체하거나 Intel backend 복원에 집중 | 더 넓은 생태계의 설계·기능을 활용할 가능성 | 현재 Intel 미지원과 구조 통합 비용을 먼저 실험해야 한다. 사용자가 원한 CT 자체 구현과도 선택을 다시 맞춰야 하므로 즉시 전환하지 않는다. |

LLVM 등 범용 compiler 기반은 필요하면 채택할 수 있다. 현재 작동하는 emitter 전체를
지금 폐기할 근거는 없다. device 함수·복잡한 주소 공간·제어 흐름 확장에서 반복적으로
막히면, 고정된 두세 커널로 직접 emitter와 LLVM/SPIR-V 경로의 의미·Windows 빌드·크기·
진단 비용을 비교한 뒤 결정한다. 다른 엔진 실행을 CT 자체 구현 성공으로 표시하지 않는다.

## 6. 다음 실행 순서 제안

### R0. 누적 구현의 검증·통합 기준 고정

산출물: PR base/head/의존성과 검토 상태 표, main~M3o 누적 변경 검토, 버전 고정한
SPIRV-Tools 검증, CPU/ABI/privacy 검증과 Arc 회귀 실행표. export마다 resolver와 behavior
시험을 구분한다. 현재85/21 수치를 CI와 native 결과로 잘못 합치지 않는다.

완료 조건: 실제 통합 후보 커밋과 시험 결과가 일치하고 로컬/공개 artifact 경계가 명확하다.
main 병합은 이 후보를 사용자에게 제시한 뒤 별도로 결정한다. 이번 검토는 병합하지 않는다.

### R1. P18a — 실행할 앱과 artifact를 먼저 고정

R1의 조사·artifact 고정은 R0와 병행할 수 있다. 누적 검증 전체가 끝날 때까지
앱 조사를 미루지 않으며, 기능 구현 전에 통합 기준을 확인한다.

산출물: applications.json과 간단한 의존성/최초 실패 보고서. 초기 집합은 기존 Driver 샘플,
보통의 동기 Runtime 내장 모듈 프로그램, 다른 분야의 독립 공개 앱 후보로 구성한다.
NVIDIA CUDA Samples v12.0 vectorAddDrv와 vectorAdd는 조사 시작 후보이며,
이번 문서가 새 Runtime artifact나 세 번째 앱 선정을 완료했다는 뜻은 아니다.

기록 항목: 저장소/태그/커밋, 소스·배포 artifact 구분, 빌드 recipe/toolchain,
EXE·GPU 코드·의존 DLL 해시, 정적/동적 cudart, PTX 유무/버전, import/동적 조회,
필수 API/명령/라이브러리, 정답·허용 오차, 실행 명령, 최초 실패와 증거 단계.

완료 조건: 우선 실행할 기존 artifact 하나와 그 artifact의 실제 최초 차단 기능이
고정된다. SASS-only, 복잡한 전용 라이브러리 의존 또는 정답 부재면 사유를 기록하고
첫 대상을 조정한다. 앱 소스를 CT에 맞게 수정해서 통과시키지 않는다.

### R2. P05 — primary context와 공유 상태

산출물: retain/release/reset, TLS current context, 명시적/primary context 상호작용,
여러 host thread·소비자의 자원 수명 계약. 미래 Runtime DLL도 하나의 CT Driver 상태를 사용한다.

완료 조건: 두 thread/소비자, reset 후 stale resource, 잘못된 소유권, 실패 경로를 검사하고
선택한 Driver 소비자가 Arc에서 정상 작동한다. P03 전체 완료를 기다릴 필요는 없다.
모호한 reset/소유권은 메모리·Runtime 확장 전에 해결한다.

### R3. P06a + 필요 P03/P04 — 선택 앱의 최소 차단 기능

산출물: 앱에서 실제 확인한 D2D/memset·속성·인자/주소/명령 형태의 좁은 공통 구현.
P06 전체의 pinned/2D/3D를 단순 Runtime 소비자의 불필요한 선행 조건으로 두지 않는다.

완료 조건: 최소 재현의 RED→GREEN뿐 아니라 고정 앱 artifact의 최초 실패가 사라지거나
실행 단계가 전진한다. 범위·0크기·overflow·정렬·context·해제 경계를 함께 확인한다.
두 번 연속 기능 추가가 앱의 시작/실행 문턱을 전진시키지 못하면 순서를 재검토한다.

### R4. P09a — 동기 Runtime 경로 하나 완주

산출물: R1 조사에 따라 동적 CT cudart shim 또는 기존 Runtime의 Driver 요구를 만족시키는
경로 중 하나를 선택한다. 정적 cudart는 DLL 이름 치환으로 해결된다고 가정하지 않는다.
init/등록/해제, 내장 fatbin, kernel 조회/launch, 동기 복사, Driver 혼용, TLS 오류를 포함한다.

완료 조건: executable/GPU 코드·의존성이 고정된 일반 CUDA 소비자가 로컬 bundle에서
실행되어 정답을 반환한다. DLL export 존재만으로 완료하지 않는다. 재빌드 소비자는
그 증거 단계로 표시하고 배포 바이너리 호환은 별도 문턱으로 남긴다.

### R5. 다음 앱이 요구하는 병렬 의미 또는 라이브러리

shared memory/barrier가 차단이면 P10a를 구현하며 부분 block·분기 참여·자원 제한을 검증한다.
라이브러리가 차단이면 좁은 P16 FP32 GEMM부터 인자 배치·수치 오차·handle·실행 순서를 검증한다.
warp·비동기·device 함수가 먼저 필요하면 그 의존성을 먼저 다룬다.
PyTorch는 이 경로들이 확보된 뒤 별도 소비자 집합으로 확대한다.

완료 조건: 다음 고정 앱에서 실제 계산의 정답·반복성을 확인하고 성능을 측정·보고한다.
성능 합격 기준은 선정 앱의 기준 측정 후 별도로 고정한다.
barrier divergence/warp 가정이 현재 IR로 보존되지 않으면 API를 늘리기 전에 실현성을 실험한다.

## 7. 검증 정책과 유보 범위

- Arc 실제 실행과 CPU 독립 정답은 계속 개발의 근거로 사용한다.
- AMD 실장비·NVIDIA 원본 비교/공존은 미검증으로 남기며, 없다는 이유로 Arc 개발을 중단하지 않는다.
  다만 기존 v0.1/일반 앱 릴리스의 모든 문턱을 통과했다고 표시하지 않는다.
- parser/type/codegen/API behavior, compiler가 생성한 PTX corpus, native GPU,
  전체 앱, 성능·반복성 결과를 분리한다. 대량 원소 수보다 새 앱/새 의미의 coverage를 함께 기록한다.
- 하위 에이전트는 독립 검토를 맡고, 구현자 GPU 실행과 별개인 검토 범위를 보고한다.
- 개인정보·키·사용자 경로·raw log·vendor/generated binary 공개를 막는 기존 규칙을 유지한다.
  이번에도 기존 미커밋 LICENSE/Cargo/README 내용은 변경하거나 공개 커밋에 섞지 않는다.

## 8. 이번 검토의 근거와 한계

작성자가 코드·결과 문서·현재 공개 PR/main 상태와 위 공식 자료를 확인했고,
두 독립 하위 에이전트가 각각 구현 범위와 계획/완료 문턱을 읽기 전용으로 검토했다.
두 검토 모두 앱 목록 부재, P03 중심 개발의 한계, P05/P06/P09와 P18 우선순위에 동의했다.
manifest의 behavior 참조 개선과 원본/재빌드 artifact 구분도 반영했다.

이번 작업은 새 GPU 실행, 외부 대체 도구 설치·성능 비교, 전체 누적 코드의 결함 없는
보증, 새 라이선스 판단 또는 일정/완료율 산정을 하지 않았다. 이 문서는 제안된 방향이며
구체적 앱 선정 뒤 다음 구현 묶음의 파일·ABI·실패 시험을 별도 상세화한다.
