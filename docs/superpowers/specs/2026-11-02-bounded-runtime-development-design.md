# Bounded Runtime development

The user asks to resume Intel CUDA compatibility work without accumulating local cache data, using the existing private Google Drive archive. They explicitly keep recovery keys only on the notebook and previously delegated routine implementation choices.

Chosen approach (implementation decision): retain the current working source, pinned tools and latest accepted evidence locally; guard new allocations; archive each new accepted run together with its immutable source checkpoint as a small encrypted unit. A mounted Drive build directory would require a new synchronization layer and can break hash-bound evidence. Repacking the entire historical cache every iteration wastes time and storage. The existing monolithic backup supports whole-archive restore only; selective historical restore is not claimed.

Local defaults: a 40 GiB project `.cache` ceiling and 30 GiB free-disk floor. Before a new native capture reserve 2 GiB conservatively, without assuming compression or deduplication. Before clean CPU validation the operator runs the same guard for the primary workspace. Refuse an operation before creating its run directory if either limit would be crossed. No automatic recursive removal is part of the guard. Manual Cargo commands outside this guarded workflow are outside its enforcement scope.

The R2r diagnostic extends the accepted R2q 20-child capture with two explicit virtual-policy samples (12000 and 12090) and two fresh strict controls. Forward actual attributes 75 and 76 using the existing explicit software target; require 5 and 2 respectively, then observe the actual unsupported attribute 15 (801/output 0). This is an experimental software target, not physical NVIDIA compute capability. Default strict returns 801/output 0 for 75; production version stays unsupported. No new production Rust behavior, exports, guard bypass or application-success claim.

Preserve source-bound parent audits, callbacks, restoration/unload and lifetime checks. Every native child uses authenticated source/tools/provider identities and a fresh sanitized environment. Strict post-controls actually query attribute 75, rather than relying on an earlier version failure. Unexpected calls/results stop the pipeline.

Storage lifecycle: source freeze -> clean CPU validation -> fresh native capture -> saved audit -> encrypted per-run/source archive -> Drive upload/readback/hash/full archive verification -> retain newest working evidence; remove only that operation's independently reproducible CPU target and temporary archive/readback copies. Future older evidence can be reclaimed only with an exact archive receipt and dependency review; newest SDK/rlib/rmeta dependencies must not be removed by name alone. Failed runs remain labelled failed and retry growth is subject to the same guard. Keys, account data and credentials never enter upload selection.

Existing root work is intentionally dirty. Use the project's private immutable source-candidate mechanism; do not stage/commit/push the root or edit externally managed worktrees. Preserve HEAD/index and protected 11 files. Record rulings/progress under ignored `.cache/r2r-work`, rather than adding a second worktree or changing root Git ignore/branch state.
