# CT 개발 전략 및 단계별 계획

작성일: 2026-10-18

상태: 검토용 설계 초안. 아래 기술 선택은 제안이며 구현·호환성 검증은 아직 수행하지 않았다. 이 문서는 전체 로드맵이다. 각 단계의 실행 계획은 선행 실험 결과를 반영해 별도로 확정한다.

## 1. 목표와 성공의 의미

CT(Cuda Translater)의 장기 목표는 CUDA에 의존하는 여러 프로그램을 Intel·AMD GPU에서 실행하도록 하는 범용 호환 계층이다. 특정 AI 모델 한 개의 이식이나 소스 변환기만으로 목표를 달성했다고 판단하지 않는다.

사용자는 장기적으로 GPU를 선택하고 CT를 통해 지원되는 기존 프로그램을 실행한다. GPU 제조사, 운영체제, 드라이버, CUDA API, 커널 명령, 수학 라이브러리별로 지원 범위를 공개한다.

초기 성공 기준은 다음과 같다.

1. 동일한 x86-64 호스트 실행 파일과 동일한 PTX 파일을 수정·재컴파일하지 않고 Intel·AMD GPU에서 각각 실행한다. GPU별 CT 패키지와 드라이버 설치는 허용한다.
2. 메모리 복사와 CUDA Driver API를 통해 실행하는 제한된 커널들의 결과가 독립 CPU 기준값과 일치한다.
3. 지원하지 않는 API·명령·입력은 원인을 표시하며 실패한다. CPU 대체 실행을 GPU 성공으로 보고하지 않는다.
4. 실제 시험한 장비·버전·실행 로그를 공개한다. 한 GPU에서 성공한 결과를 모든 Intel·AMD GPU 지원으로 일반화하지 않는다.

첫 데모가 외부 PTX를 사용하는 제어된 프로그램이라는 점도 명시한다. 이것은 임의의 CUDA 프로그램, fatbin 내장 프로그램, PyTorch 패키지의 호환성을 뜻하지 않는다.

## 2. 기존 기술과 CT의 위치

2026-10-18에 프로젝트 공식 문서와 저장소를 확인했다. 아래 설명은 문서상의 범위이며 CT 환경에서 재현한 결과가 아니다.

| 기술 | 역할 | CT에서의 활용 및 한계 |
| --- | --- | --- |
| HIPIFY / HIP | CUDA 소스를 HIP으로 이식하고 관련 GPU 실행 환경 제공 | AMD 백엔드·라이브러리 활용 후보. 이것만으로 Intel GPU나 기존 CUDA 실행 파일 호환성이 생기지는 않는다. |
| SYCLomatic | CUDA 소스를 SYCL로 이식하도록 지원 | 소스가 있는 프로젝트의 보조 경로 및 비교 기준. 변환 후 개발자의 수정·검증이 필요할 수 있다. |
| AdaptiveCpp | 여러 제조사의 장치를 겨냥하는 이종 컴파일러; PCUDA는 실험적 | 소스 재빌드 경로의 대안 후보. 소스 수준의 이식과 기존 CUDA 바이너리 호환을 구분한다. |
| ZLUDA | 비 NVIDIA GPU용 CUDA 대체 계층 | 목표와 가장 가까운 재사용·기여 후보. 현재 Intel·AMD 지원 범위와 CT에 필요한 커널·API는 버전을 고정한 실험으로 확인한다. |

CT의 가치는 기존 기술의 이름을 바꾸는 데 있지 않다. 재사용 가능한 엔진 위에 Intel·AMD 실행 경로, 명확한 지원 진단, 재현 가능한 호환성 검증을 제공하는 데 둔다. 평가 결과 CT가 독립 엔진보다 기존 프로젝트의 Intel 백엔드·진단 기여로 구현되는 편이 낫다면 그 경로를 우선한다.

## 3. 접근 방식 비교와 권장안

### A. 소스 변환 중심

CUDA 소스 → HIP / SYCL / PCUDA → 재컴파일. 기존 컴파일러를 활용할 수 있으나 소스와 재빌드가 필요하다. 사용자가 원하는 범용 실행 호환성의 일부만 해결한다.

### B. 실행 시 호환 계층 중심 — 권장

기존 프로그램의 CUDA 호출을 받고, 사용 가능한 PTX를 대상 GPU 코드로 변환하며, 라이브러리 호출을 대응 구현으로 연결한다. 사용자 목표에 가장 가깝다. ABI, 명령 의미, 메모리·동기화, 라이브러리마다 별도 작업이 필요하므로 작은 지원 범위부터 확장한다.

### C. 소스·바이너리 경로 동시 개발

폭넓은 입력을 받을 수 있지만 컴파일러·런타임·진단·패키징을 동시에 유지해야 한다. 초기에는 선택하지 않는다. 소스 이식은 이후 별도 하위 프로젝트로 다룬다.

권장 순서는 B의 기존 엔진 재사용 가능성 평가 → PTX 기반 최소 호환 계층 → 일반 프로그램 로딩 → 수학 라이브러리 → 실제 AI 프로그램이다. 완전 독자 컴파일러 개발은 기존 기술을 재사용할 수 없다는 증거가 나온 경우에만 선택한다.

## 4. 제안 구조

```text
기존 CUDA 호스트 프로그램
        |
        v
CT 로더 / CUDA Driver API ABI 계층
        |                          |
        v                          v
장치·컨텍스트·메모리·스트림 관리   모듈/PTX 로더
        |                          |
        |                    PTX 의미 해석·변환
        |                          |
        +-------- 백엔드 인터페이스 --+
                        |
              +---------+----------+
              |                    |
        Intel 백엔드          AMD 백엔드
        Level Zero 등 후보    HIP/ROCm 등 후보
              |                    |
           Intel GPU            AMD GPU

별도 확장: CUDA Runtime API / fatbin 등록 / cuBLAS 등 라이브러리 어댑터
별도 도구: ct doctor / ct inspect / ct run / 검증·벤치마크
```

PTX는 NVIDIA의 가상 명령어 체계다. NVIDIA 기계어인 SASS/cubin과 구분한다. PTX를 다른 GPU 명령으로 내리는 과정은 이름 치환이 아니라 타입·주소 공간·제어 흐름·병렬 실행 의미를 보존하는 컴파일 과정이다. LLVM이나 SPIR-V를 선택해도 NVIDIA 전용 의미가 자동으로 해결되지는 않는다.

Intel 경로는 Level Zero와 SPIR-V 또는 기존 엔진의 지원 경로, AMD 경로는 HIP/ROCm과 기존 엔진의 코드 생성 경로를 비교한다. HIP에 PTX를 그대로 넘기는 방식은 전제하지 않는다. 공통으로 관리할 것은 장치/메모리/모듈/실행 의미이며, 벤더별 코드 생성과 자원 제약은 백엔드에 둔다.

수학 라이브러리는 커널 변환만으로 해결되지 않는다. cuBLAS 등의 공개 API별로 행렬 배치, 전치, 정밀도, 스트림, 오류 동작을 맞추는 별도 어댑터가 필요하다.

## 5. 첫 버전의 범위

### v0.1 목표

- x86-64 Linux 한 배포판을 초기 기준 환경으로 제안한다. 정확한 배포판·드라이버·툴체인은 0단계에서 양쪽 GPU 지원을 확인해 고정한다.
- Intel GPU 한 모델, AMD GPU 한 모델에서 동일한 테스트 묶음을 실행한다. 모델 미확보 시 해당 경로는 미검증으로 남긴다.
- 단일 프로세스·단일 GPU·명시적 장치 메모리·동기 실행 위주로 시작한다.
- 외부 PTX 파일을 읽고 제한된 CUDA Driver API로 실행하는 프로그램을 대상으로 한다.
- 기본 커널: 벡터 덧셈, SAXPY, 원소별 ReLU, 단순 FP32 행렬곱. 최적화된 BLAS나 실제 신경망 전체 실행이라고 부르지 않는다.
- 정수 연산은 정확 일치, FP32는 유한 입력에 대해 abs(actual - expected) <= 1e-5 + 1e-4 * abs(expected)를 기본 판정으로 제안한다. 테스트가 이 허용오차를 만족하지 못하면 원인을 확인하며 통과를 위해 임의 완화하지 않는다.

### v0.1에서 제외

- PTX 없는 SASS/cubin 전용 프로그램, 모든 CUDA 버전, 32비트 호스트.
- 임의의 PyTorch CUDA wheel, TensorRT, cuDNN, NCCL 전체 호환.
- 멀티 GPU·분산 학습·CUDA Graphs·동적 병렬 실행·Unified Memory 전체.
- Tensor Core/MMA, warp 의존 알고리즘, 고급 atomic 및 메모리 모델 전체.
- Windows 네이티브 지원 보장. Windows는 별도 로더/ABI/배포 검증이 필요하다.

이 항목들은 영구 포기가 아니라 별도 확장 과제다. 특히 Windows와 AI 프레임워크는 기반 실행 경로가 검증된 뒤에 다룬다.

## 6. 개발 단계와 통과 기준

### 0단계 — 실험 환경과 재사용 전략 확정

산출물: `docs/environment-matrix.md`, `docs/engine-evaluation.md`, `docs/decisions/0001-engine-and-backends.md`.

- 보유/접근 가능한 Intel·AMD·NVIDIA GPU, 운영체제, 드라이버를 확인한다. NVIDIA GPU는 원본 CUDA 차등 검증용이며 CPU 기준값은 별도로 유지한다.
- ZLUDA 등 후보의 태그/커밋, 라이선스, 빌드 조건, 지원 API를 기록한다. 문서상의 지원과 실제 재현 성공을 구분한다.
- Intel·AMD에서 각각 네이티브 벡터 덧셈을 먼저 실행해 드라이버와 도구 문제를 분리한다.
- 동일 PTX 벡터 덧셈의 기존 엔진 실행을 시도해 재사용 가능한 경로와 없는 경로를 확인한다.
- 주 경로를 기존 엔진 통합/포크/기여 또는 제한적 독자 구현 중 하나로 결정한다. 의존성 버전과 NOTICE 요구를 정리한다.

통과: 양쪽 장치 접근, 네이티브 실행, 선택한 경로의 가능성 증거와 실패 원인, 고정할 버전 목록이 문서화되어야 한다. 장비가 없거나 Intel 코드 생성 경로가 성립하지 않으면 구현 성공을 가정하지 않고 이 단계의 실험 결과를 검토한다.

### 1단계 — 진단과 테스트 계약

산출물: `ct doctor`, `ct inspect`, 버전 있는 JSON 결과 형식, 초기 지원 표, 합성 테스트 입력.

- doctor는 장치·드라이버·백엔드 버전·필수 도구를 보고한다.
- inspect는 처음에는 외부 PTX의 버전·entry·사용 명령을 분석한다. 검토하지 못한 내용은 unknown으로 보고한다. 실행 파일/fatbin 전체 분석은 4단계다.
- 테스트 상태는 pass / fail / skip / unsupported로 구분한다. 필요한 GPU가 없는 실행은 pass가 아니다.
- CI에서는 GPU 없이 가능한 파싱·에러 경로를 검증하고, 실제 GPU 시험은 별도 작업으로 분리한다.

통과: 누락된 드라이버, 잘못된 PTX, 지원하지 않는 명령, 여러 장치 선택의 테스트가 기대한 진단을 낸다. 정적 분석만으로 실행 가능하다고 확정하지 않는다.

### 2단계 — CUDA ABI와 기본 자원 관리

초기 API 후보: `cuInit`, `cuDriverGetVersion`, `cuDeviceGetCount`, `cuDeviceGet`, `cuDeviceGetName`, `cuDeviceGetAttribute`, `cuCtxCreate`/`cuCtxDestroy`의 선택 버전, `cuMemAlloc`/`cuMemFree`, `cuMemcpyHtoD`/`cuMemcpyDtoH`, `cuCtxSynchronize`, 오류 조회 API. 정확한 심볼 접미사와 서명은 고정 CUDA 헤더 및 선택 엔진에 맞춰 확정한다.

- 별도 디렉터리의 CT 라이브러리를 실행 단위로 로딩한다. 시스템 CUDA 라이브러리를 덮어쓰지 않는다.
- CPU 핸들과 GPU 주소를 구분하고 컨텍스트 소유권·생명주기를 정의한다.
- 현재 단계에서 구현하지 않은 API를 성공으로 응답하지 않는다.
- 범위 밖 복사, 잘못된 핸들, 해제 후 사용, 할당 실패를 시험한다.

통과: Intel·AMD에서 할당→호스트/장치 왕복 복사→검증→해제가 통과한다. 반복 작업 후 CT가 추적하는 미해제 자원이 0이어야 하며 비동기 GPU 오류도 관찰한다.

### 3단계 — PTX 커널 실행, v0.1 후보

추가 API 후보: `cuModuleLoadData`, `cuModuleGetFunction`, `cuLaunchKernel`, `cuModuleUnload`.

- 실제 테스트 커널이 사용하는 PTX 버전·타입·명령만 먼저 지원 목록에 고정한다.
- 인자 크기·정렬, 스레드/블록 인덱스, 포인터 산술, 전역 메모리, 정수/FP32 연산, 조건 분기부터 검증한다.
- 고정된 입력 파일의 해시가 양쪽 실행에서 동일한지 확인한다.
- 0, 1, block_size-1, block_size, block_size+1, 큰 비정렬 길이를 시험한다. 길이 0은 호스트에서 실행을 생략하고, 잘못된 0차원 launch와 구분한다.
- NaN/Inf·부동소수점 특수값은 별도 의미 테스트로 관리한다. warp·barrier·shared memory가 필요한 테스트는 지원 전에는 명시적으로 제외한다.

통과: 동일한 호스트 실행 파일·PTX로 벡터 덧셈/SAXPY/ReLU/단순 행렬곱이 양쪽 GPU에서 CPU 기준값과 비교해 통과한다. 장치 실행 증거가 필요하며 CPU 대체 실행은 허용하지 않는다.

### 4단계 — 일반 프로그램 로딩, v0.2 후보

- PTX 포함 fatbin을 검사하고 호환 PTX를 선택한다. SASS만 있거나 PTX 버전이 지원 범위 밖이면 원인을 알린다.
- CUDA Runtime API, 정적/동적 cudart 차이, 커널 등록, 드라이버 진입점 조회, 기본 스트림 의미를 분리해 지원한다.
- 스트림·이벤트·비동기 복사를 추가하면서 수명/순서/동기화 오류를 검증한다.
- 기존 오픈소스 프로그램 한 개를 고정 버전·입력으로 선택하고 원본 실행 파일을 수정하지 않은 실행을 검증한다.

통과: 외부 PTX 데모 밖의 프로그램을 양쪽 GPU에서 실행한다. API 지원률은 검증한 집합에 대해서만 보고한다.

### 5단계 — 수학 라이브러리와 작은 AI 워크로드, v0.3 후보

- 먼저 cuBLAS FP32 GEMM의 좁은 API 집합을 택한다. Intel·AMD 대응 라이브러리의 배치·전치·leading dimension·스트림·오류 동작을 검증한다.
- 작은 MLP 추론처럼 고정 가중치·고정 입력을 쓰는 독립 프로그램을 검증한다.
- 실제 AI 앱 하나의 API/라이브러리 사용을 조사하고 누락 의존성을 목록화한 후 통합을 결정한다.
- PyTorch CUDA wheel 호환은 별도 마일스톤이다. GEMM 성공을 근거로 프레임워크 전체가 실행된다고 주장하지 않는다.

통과: CPU/원본 기준과 수치 비교, 두 벤더 실행, 누락 API 0건이라는 해당 워크로드 한정 증거가 있어야 한다. 일반 AI 호환성 주장은 하지 않는다.

### 6단계 — Windows와 배포 확대

- Windows 로더, DLL 검색, 호출 규약, 드라이버 조합을 별도 시험한다. Linux/WSL 통과는 Windows 네이티브 통과와 분리한다.
- GPU 제품군별 커뮤니티 재현, 오류 리포트 양식, 호환성 데이터베이스를 제공한다.
- 이후 FP16/BF16, 고급 동기화/warp 연산, cuDNN·FFT·sparse, 다중 GPU를 수요와 실현 가능성 순서로 별도 계획한다.

통과: OS·GPU·드라이버·도구 버전별 재현 로그와 설치/제거/기존 CUDA 환경 복구 시험이 존재한다.

## 7. 검증과 성능 측정 원칙

- 정확성: 독립 CPU 기준, 가능하면 원본 NVIDIA 실행, Intel·AMD 결과를 함께 비교한다. NVIDIA와 수치가 같다는 것만으로 독립 정답 검증을 대체하지 않는다.
- 미지원 검증: API/명령/장치 조합별 예상 실패를 시험하고 성공으로 위장하지 않는지 확인한다.
- 병렬 의미: shared memory, barrier, warp/subgroup, atomic, 메모리 순서의 지원은 각각 독립적인 통과 기준을 둔다.
- 재현성: CT/엔진 커밋, GPU 식별자, OS, 드라이버, 툴체인, 입력 해시, seed, 로그, 시험 상태를 결과에 포함한다.
- 성능: 첫 컴파일, 캐시 재사용, 전송, 커널, 전체 시간을 나눈다. 초기 벤치마크는 워밍업 5회·측정 30회로 시작하고 중앙값 및 변동을 기록한다. 재컴파일이 섞였는지도 기록한다.
- 같은 GPU의 네이티브 구현 대비 오버헤드를 주 비교값으로 삼는다. 서로 다른 GPU 간 시간 차이를 CT의 순수 변환 비용으로 해석하지 않는다.
- 초기 릴리스는 특정 속도 배율을 보장하지 않는다. 잘못된 결과나 미지원 연산이 남은 경로를 성능 성공으로 발표하지 않는다.

## 8. 코드 구조와 기술 선택 제안

다음은 역할 경계이며 아직 생성하거나 확정한 코드 구조가 아니다. 기존 엔진 통합을 선택하면 그 프로젝트의 구조를 따른다.

```text
docs/decisions/       엔진·백엔드·지원 범위 결정과 근거
docs/compatibility/   OS/GPU/API/PTX/라이브러리 지원 표
cli/                 doctor / inspect / run
runtime/             CUDA ABI, 컨텍스트·자원 생명주기
compiler/            PTX 분석·의미 변환 또는 재사용 엔진 연결
backends/intel/      Intel 장치·코드 로딩·실행
backends/amd/        AMD 장치·코드 로딩·실행
libraries/           CUDA 라이브러리별 대응 어댑터
tests/               합성 입력, API/명령/오류/종단 검증
benchmarks/          원본·네이티브·CT 비교 및 결과 형식
```

ABI/런타임 언어는 기존 엔진을 활용할 경우 그 언어를 우선한다. 독자 구현이면 Rust 및 C ABI를 우선 평가하되 LLVM/벤더 SDK 통합 비용을 확인한다. 시험 자동화에는 Python, 빌드에는 기존 엔진의 빌드 도구를 사용한다. 컴파일러와 벤더 SDK 버전은 0단계에서 조합을 재현한 뒤 잠근다.

## 10. 작업 순서와 일정 해석

현재는 GPU 모델, 실험 장비, 엔진 재현 비용이 확정되지 않아 완료 날짜를 제시하지 않는다. GPU 호환 계층은 월 단위로 끝나는지조차 선행 실험 없이는 확정할 수 없는 연구개발이다.

첫 작업 묶음은 다음 순서로 제한한다.

1. 장비와 OS 접근 확인.
2. 버전 고정한 기존 엔진의 코드/라이선스/빌드 조건 조사.
3. 두 벤더 네이티브 벡터 덧셈.
4. 같은 PTX를 실행하는 최소 경로 비교.
5. 결과를 토대로 엔진·백엔드 선택 문서와 1차 실행 계획 작성.

각 단계는 테스트가 통과해야 다음으로 이동한다. 테스트 장비나 번역 경로가 확보되지 않으면 선행 조건을 해결하거나 목표 범위를 다시 검토한다. 미검증 단계를 완료로 표시하지 않는다.

## 11. 현재 사실과 미확정 사항

- 확인: 저장소에는 프로젝트 소개와 `.gitignore`만 있었으며 구현은 없다.
- 확인: 현재 세션은 Windows 환경이다. GPU 정보의 CIM 조회는 권한 제한으로 실패했다.
- 미확정: 실제 GPU 모델, Linux 장비 접근, SDK 설치, 기존 엔진 빌드/실행 가능성, 지원 버전.
- 제안: 바이너리 호환 중심, 기존 엔진 우선, PTX 기반 제한 데모, 양쪽 GPU 검증, Linux 기준 환경부터 시작.
- 아직 수행하지 않음: 의존성 설치, 외부 엔진 코드 실행, CUDA/PTX 실행 시험, 프로젝트 기능 구현.
